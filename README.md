# TopDownRts — каркас игры (заметка «как всё устроено»)

Проект: `~/Study/rts/` (решение `TopDownRts.sln`, .NET 8, C#).
Это **каркас** RTS с видом сверху на нескольких кораблей, строящийся по дисциплине курса
ООАиП: **сначала интерфейсы → затем тесты → затем классы-реализации** (TDD).
Домен взят из Event Storming-доски «Космические корабли (RTS, 2D)».

---

## 1. Как запустить

```bash
cd ~/Study/rts
dotnet test          # прогон всех тестов (сейчас 24, все зелёные)
dotnet build         # просто сборка
```

Каждый проект — своя DLL, тесты — xUnit. Тесты — это «живая документация»: любое
поведение каркаса можно прочитать как юнит-тест с говорящим именем.

## 3. Как читается проект (принцип ООАиП)

Везде одна и та же тройка — именно в этом порядке мы делали работу:

1. **Интерфейсы** («что должно уметь», без слов «как»):
   `IPlayerAuthenticator`, `IMatchmakingService`, `IFleetRegistry`, `ICombatService`,
   `IRatingRepository`. Рядом лежат маленькие записи-данные: `Match`, `Fleet`, `ShipUnit`,
   `PlayerRating`, `AuthResult`.
2. **Тесты** («как должно работать»). Формулируются как сценарии игры, не как вызовы методов:
   «Двое в очереди соберутся в матч», «щит гасит часть урона», «код одноразовый».
   Тесты знают только интерфейсы — поэтому реализации можно переписывать спокойно.
3. **Классы-реализации** («как работает»). Простые, in-memory, без БД/сети.
   Сущности маленькие: чем меньше класс, тем дешевле завтрашняя правка.

Проводить правку можно всегда по тому же циклу: правишь интерфейс → дополняешь тесты
(сначала падают) → реализуешь → прогон зелёный.

## 4. Логика кусков (простым языком)

### 4.1 Аутентификация (правило 2FA — твоё, 08.10)

Поток: игрок уже введённый пароль правильный. Дальше решение — **только по токену устройства**:

- сохранённый токен игрока найден и совпал с предъявленным → второй этап не нужен, пуск;
- токена нет (первый вход) или НЕ совпал → генерируется одноразовый код (6 цифр),
  код сохраняется, письмо с кодом уходит на почту игрока; статус `PendingEmail`;
- игрок ввёл код: верный → пуск + токен устройства ЗАПОМИНАЕТСЯ (следующий вход — сразу);
  неверный / уже использованный / заменённый новым → отказ.

Правила честности: код гасится при проверке (повторный ввод того же кода — отказ),
новая попытка входа перезаписывает старый код — принимается только последний.

### 4.2 Лобби (очередь → матч)

- `Join` ставит игрока в очередь. Двое — матч собрался (событие `MatchFound`).
- `Ready` — подтверждение готовности; от обоих → `BothReady` (бой можно начинать).
- `Tick(время)` — служебный такт лобби: кто не успел подтвердить за `ReadyTimeout`
  (из конфига, сейчас 30 с) — лобби сбрасывается (`TimedOut`), оба игрока свободны.
- `Decline` — один отказался, оба свободны.

### 4.3 Флоты

- `SetFleet` — записать состав (`FleetUpdated`); каждую новую правку сбрасывает подтверждение.
- `ConfirmFleet` — состав зафиксирован (`FleetConfirmed`); без выставленного состава не вызывается.
- Корабль: `ShipUnit` (id, класс, корпус, щит; `Destroyed` = корпус ≤ 0).
- Флот: `Fleet` (владелец, команда, список кораблей; `IsWiped` = все мертвы).

### 4.4 Бой (тики)

Механика одного тика (`Tick`):

1. Если бой окончен — тик ничего не делает.
2. Команда A наносит урон: **число живых кораблей × BaseDamagePerTick**.
3. Урон целим в **первый живой корабль** противоположной команды.
4. Щит цели гасит `min(ShieldAbsorbsPerTick, щит)` урона (щит уменьшается),
   **остаток урона идёт в корпус** (это и есть `HullDamageToTeam…`).
5. Корпус ≤ 0 → корабль уничтожен. Все корабли команды мертвы → бой окончен (`IsOver`).

Пример с числами по умолчанию (урон 10, гашение 6): у цели щит 10/корпус 100 →
после тика щит 4, корпус 96; следующий тик — гашение 4 (весь остаток щита), корпус 90 и далее по 10.

### 4.5 Рейтинг и статистика

- `RecordOutcome(победитель, проигравший)`: победителю `+RatingWinPoints`, проигравшему
  `−RatingLosePoints`, счётчики побед/поражений растут.
- Числа — из того же `BalanceConfig` (сейчас +15 / −10).

## 5. Все спорные числа — в одном месте

**`BalanceConfig`** (в `src/Rts.Domain/Interfaces.cs`) — единственная точка правок чисел:

```csharp
new BalanceConfig
{
    ReadyTimeout = TimeSpan.FromSeconds(30), // таймаут лобби
    BaseDamagePerTick    = 10,               // урон за тик
    ShieldAbsorbsPerTick = 6,                // сколько урона гасит щит
    RatingWinPoints  = 15,
    RatingLosePoints = 10,
}
```

**Правило:** менять числа = править этот конфиг. Тесты каждый задаёт СВОЙ конфиг,
поэтому изменения дефолтов не ломают тесты. То же самое касается будущих механик:
тик боя, радиус/урон метеорита, параметры 4 классов кораблей — всё это заводим
в `BalanceConfig`, а не «в код».

## 6. Соответствие Event Storming (доска v5, 8 кадров)

| Кадр (доска) | События/команды по доске | В каркасе | Статус |
| --- | --- | --- | --- |
| 0. Вход и профиль | Register, Вход+2FA → PlayerAuthenticated, Почтовый сервис (ext) | `Rts.Auth`: TwoFactorAuthenticator + IEmailCodeSender | ✅ покрыт (без регистрации профиля — это следующий кусок) |
| 1. Пользователи и меню | комнаты, вход в комнаты | — | ⛔ не начинали (UI/комнаты) |
| 2. Конструктор правил | пресеты, валидация (P4, P5) | — | ⛔ ждёт подтверждения хотспотов правил |
| 3a. Сбор матча | QueueJoined→P1→MatchFound, ReadyUp, ReadyTimeout (P2), дуэли (P3) | `LobbyService`: пара→матч, Ready, таймаут-сброс, Decline | ✅ ядро покрыто |
| 3b. Выбор флота | SelectShips/FleetUpdated, ConfirmFleet (P6 кап 100, P7 старт боя) | `FleetRegistry`: SetFleet/ConfirmFleet; `MatchOrchestrator`: AllFleetsConfirmed (после BothReady) → MatchStarted → бой | ✅ связка 3b→4b покрыта (P6 капа нет) |
| 4a. Карта | Movement, форсаж, метеориты (P8–P10, P17) | — | ⛔ ждёт подтверждения чисел |
| 4b. Бой по тикам | DamageApplied (P12), ShieldAbsorbed (P13), ShipDestroyed, FleetWipedOut, BattleEnded (P14), Concede | `CombatService`: тик урона/щита/гибели, `IsOver` | 🟡 ядро есть: нет P11 (попадание от дистанции) и Concede |
| 5. Итоги | UpdateRating→RatingService **(Эло)** (P15), StatsRecorded (P16) | `RatingRepository`: ±points, счётчики | 🟡 упрощение: НЕ Эло, без «только 1v1-рейтинг» |

**Сознательные упрощения каркаса** (не баги, а осознанные границы MVP):
- Автоподбор лобби — «первая пара в очереди», а не подборе по рейтингу (P1 уточнится, когда появится рейтинг в лобби-сервисе).
- Попадание = всегда (нет дистанции/классов — P11 ждёт своих данных с доски).
- Рейтинг — простой ±N, а не Эло (P15 называет RatingService внешним сервисом — заимствуем формулу позже).
- Нет дуэлей-приглашений (P3) и Concede — короткие механики, добавим по надобности.
- Ничья в рейтинге — открытый вопрос доски (хотспот кадра 5).

## 7. Что НЕ нужно переделывать при завтрашних правках

Завтра по плану: внос правки 2FA в доску + подтверждение хотспотов (метеорит, классы
кораблей, тик/DPS/HP, параметры щита, базы). Эти правки вписываются так:
- числа → **только** `BalanceConfig` (+1 строка на новое число, тесты задают свой конфиг);
- новая механика (метеорит, классы) → новый интерфейс/политика в `Interfaces.cs`,
  тесты (красные) → реализация; остальное не трогается;
- доска ES (`~/AI/es`, Vault .drawio) — источник контента: любое изменение правила
  сначала в модели, потом в каркасе — так доска и код не расходятся.

## 8. Словарик (для быстрого чтения кода)

- **Интерфейс** — контракт: имена методов, что должны означать, без реализации.
- **Реализация** — конкретный класс, работающий с обычной памятью (in-memory): дальше за
  этим же интерфейсом может встать БД/сеть, код выше не узнает.
- **Политика** — «правило, которое решает»: при каком событии что запускать
  (пример: TwoFactorAuthenticator, правило таймаута лобби, правило гашения щита).
- **Конфиг баланса** — все изменяемые числа игры в одном record.
- **TDD-цикл** — тесты первыми (красные) → реализация до зелёного прогона.
