# TopDownRts — каркас игры (заметка «как всё устроено»)

Проект: `~/Study/rts/` (решение `TopDownRts.sln`, .NET 8, C#).
Это **каркас** RTS с видом сверху на нескольких кораблей, строящийся по дисциплине курса
ООАиП: **сначала интерфейсы → затем тесты → затем классы-реализации** (TDD).
Домен взят из Event Storming-доски «Космические корабли (RTS, 2D)».

---

## 1. Как запустить

```bash
cd ~/Study/rts
dotnet test          # прогон всех тестов (сейчас 130: 21 Auth + 109 Domain, все зелёные)
dotnet build         # просто сборка
```

Каждый проект — своя DLL, тесты — xUnit. Тесты — это «живая документация»: любое
поведение каркаса можно прочитать как юнит-тест с говорящим именем.

## 3. Как читается проект (принцип ООАиП)

Везде одна и та же тройка — именно в этом порядке мы делали работу:

1. **Интерфейсы** («что должно уметь», без слов «как»):
   `IPlayerAuthenticator`, `IMatchmakingService`, `IFleetRegistry`, `ICombatService`,
   `IRatingRepository`, `IRoomService` (комнаты), `IBaseControlService` (режим баз),
   `IFleetMovementService` (движение по карте), `IGameSession` (фасад полного хода). Рядом
   лежат маленькие записи-данные: `Match`, `Fleet`, `ShipUnit`, `PlayerRating`, `AuthResult`,
   `HostRuleSet`, `MovementConfig`.
2. **Тесты** («как должно работать»). Формулируются как сценарии игры, не как вызовы методов:
   «Двое в очереди соберутся в матч», «щит гасит часть урона», «код одноразовый».
   Тесты знают только интерфейсы — поэтому реализации можно переписывать спокойно.
3. **Классы-реализации** («как работает»). Простые, in-memory, без БД/сети.
   Сущности маленькие: чем меньше класс, тем дешевле завтрашняя правка.

Проводить правку можно всегда по тому же циклу: правишь интерфейс → дополняешь тесты
(сначала падают) → реализуешь → прогон зелёный.

## 4. Логика кусков (простым языком)

### 4.1 Аутентификация (правило 2FA — твоё, 08.10)

Поток: игрок уже введённый пароль правильный. Дальше решение — **только по токену устройства**:

- сохранённый токен игрока найден и совпал с предъявленным → второй этап не нужен, пуск;
- токена нет (первый вход) или НЕ совпал → генерируется одноразовый код (6 цифр),
  код сохраняется, письмо с кодом уходит на почту игрока; статус `PendingEmail`;
- игрок ввёл код: верный → пуск + токен устройства ЗАПОМИНАЕТСЯ (следующий вход — сразу);
  неверный / уже использованный / заменённый новым → отказ.

Правила честности: код гасится при проверке (повторный ввод того же кода — отказ),
новая попытка входа перезаписывает старый код — принимается только последний.

### 4.2 Лобби (очередь → матч)

- `Join` ставит игрока в очередь. Двое — матч собрался (событие `MatchFound`).
- `Ready` — подтверждение готовности; от обоих → `BothReady` (бой можно начинать).
- `Tick(время)` — служебный такт лобби: кто не успел подтвердить за `ReadyTimeout`
  (из конфига, сейчас 30 с) — лобби сбрасывается (`TimedOut`), оба игрока свободны.
- `Decline` — один отказался, оба свободны.

### 4.3 Флоты

- `SetFleet` — записать состав (`FleetUpdated`); каждую новую правку сбрасывает подтверждение.
- `ConfirmFleet` — состав зафиксирован (`FleetConfirmed`); без выставленного состава не вызывается.
- Корабль: `ShipUnit` (id, класс, корпус, щит; `Destroyed` = корпус ≤ 0).
- Флот: `Fleet` (владелец, команда, список кораблей; `IsWiped` = все мертвы).

### 4.4 Бой (тики)

Механика одного тика (`Tick`):

1. Если бой окончен — тик ничего не делает.
2. Команда A наносит урон: **число живых кораблей × BaseDamagePerTick**.
3. Урон целим в **первый живой корабль** противоположной команды.
4. Щит цели гасит `min(ShieldAbsorbsPerTick, щит)` урона (щит уменьшается),
   **остаток урона идёт в корпус** (это и есть `HullDamageToTeam…`).
5. Корпус ≤ 0 → корабль уничтожен. Все корабли команды мертвы → бой окончен (`IsOver`).

Пример с числами по умолчанию (урон 10, гашение 6): у цели щит 10/корпус 100 →
после тика щит 4, корпус 96; следующий тик — гашение 4 (весь остаток щита), корпус 90 и далее по 10.

### 4.5 Рейтинг и статистика

- `RecordOutcome(победитель, проигравший)`: победителю `+RatingWinPoints`, проигравшему
  `−RatingLosePoints`, счётчики побед/поражений растут.
- Числа — из того же `BalanceConfig` (сейчас +15 / −10).

### 4.6 Регистрация профиля (кадр 0)

- `RegisterPlayer(id, почта)`: создаёт профиль и выдаёт событие `PlayerRegistered`.
- Пустые id/почта и повторная регистрация того же id — ошибка; `TryGet` находит профиль.
- Никаких писем/сети: регистрация — чистое хранилище; почтовые коды входа — забота 2FA.

## 5. Все спорные числа — в одном месте

**`BalanceConfig`** (в `src/Rts.Domain/Interfaces.cs`) — единственная точка правок чисел:

```csharp
new BalanceConfig
{
    ReadyTimeout          = TimeSpan.FromSeconds(30), // таймаут лобби
    BaseDamagePerTick     = 10,                       // урон за тик
    ShieldAbsorbsPerTick  = 6,                        // сколько урона гасит щит
    RatingWinPoints       = 15,
    RatingLosePoints      = 10,
    // --- кадр 3b: классы кораблей и закупка (фиксация владельца 05.11: 6 классов;
    //     ЧИСЛА ниже — дефолты, НЕ подтверждено владельцем) ---
    PurchaseCapPoints     = 100,   // капа закупа НА ИГРОКА (2v2 — по 100 каждому); дефолт созвона 24.09
    ShipClasses = new()            // Cost / Hull / Shield по классам
    {
        ["light"]   = new(5,  50,  20),  // лёгкий
        ["medium"]  = new(8,  80,  40),  // средний
        ["heavy"]   = new(12, 150, 80),  // тяжёлый
        ["support"] = new(10, 70,  50),  // поддержка
        ["scout"]   = new(4,  30,  10),  // разведка
        ["supply"]  = new(9,  60,  30),  // снабжение
    },
    UnknownClassProfile   = new(10, 100, 50), // профиль для классов ВНЕ словаря (см. правило)
}
```

**Правило:** менять числа = править этот конфиг. Тесты каждый задаёт СВОЙ конфиг,
поэтому изменения дефолтов не ломают тесты. То же самое касается будущих механик:
тик боя, радиус/урон метеорита, параметры 6 классов кораблей — всё это заводим
в `BalanceConfig`, а не «в код».

**Совместимость классов (важно):** класс корабля — строка (`ShipUnit.Class`). Класс,
которого НЕТ в `ShipClasses` (например «linac» из старых составов/тестов), не ломается:
он закупается по `UnknownClassProfile` — дефолтному профилю конфига. Так старые тесты
и старые составы продолжают работать; когда класс подтвердят владельцем, его просто
добавляют в `ShipClasses`. Капа (`SetFleet`) считается по одному правилу и для известных,
и для неизвестных классов — обойти её через неизвестный класс нельзя.

**Правила режима — хост задаёт ползунками (`HostRuleSet`, кадры 2+4a):** хост комнаты выбирает
тип режима (`Mode.BaseControl`) и значения ползунков; ползунок несёт диапазон Min..Max и заводской
Default, значение вне диапазона конструктор отвергает. Числа ниже — дефолты по аналогии с
доминацией/завоеванием (WarThunder), НЕ подтверждены владельцем; `HoldAllBasesMinutes = 10`
минут — пример владельца от 05.11 (удержание ВСЕХ баз суммарно 10 минут = победа), тоже
пока не подтверждён.

| Ползунок | Диапазон | Дефолт | Смысл |
| --- | --- | --- | --- |
| `HoldAllBasesMinutes` | 1..60 | 10 | минут непрерывного владения всеми тремя базами = победа (пример владельца) |
| `VictoryScoreThreshold` | 100..2000 | 600 | порог очков = победа |
| `OwnBaseScorePerMinute` | 1..180 | 30 | очки в минуту за свою базу |
| `CentralBaseScorePerMinute` | 1..240 | 60 | очки в минуту за центральную базу |
| `EnemyBaseScorePerMinute` | 1..180 | 30 | очки в минуту за вражескую базу |
| `CaptureSeconds` | 5..60 | 20 | секунд непрерывного присутствия для захвата базы |

**Захват по присутствию (кадр 4a):** позиции тесты/слой карты передают напрямую — кто из живых
кораблей какой команды стоит в зоне базы (`BasePresence` = база, команда, число живых),
координатной механики движения в кадре нет. В зоне только команда X непрерывно `CaptureSeconds`
— база переходит X; зона оспорена (две команды) или пуста — прогресс захвата сбрасывается.
Очки за владение капают тиками по профилю (своя/центральная/вражеская); второй путь к победе —
таймер непрерывного владения всеми тремя базами; после победы тики ничего не меняют. Всё
тикается, как бой, — без реального времени: `src/Rts.Domain/BaseControlService.cs`,
контракт — `ModeInterfaces.cs`.

**Карта и движение (`MovementConfig` в `src/Rts.Domain/MovementInterfaces.cs`, кадр 4a).**
Все числа — дефолты по аналогии со стандартными RTS, НЕ подтверждены владельцем
(правка = одна строка):

```csharp
new MovementConfig
{
    MapWidth = 2000, MapHeight = 2000,        // карта 2000×2000
    BasePoints = { HomeA = (400,1000), Central = (1000,1000), HomeB = (1600,1000) },
    BaseZoneRadius = 150,                     // радиус зоны базы
    BaseSpeedUnitsPerSecond = 100,            // базовая скорость, ед/сек
    ClassSpeedMultipliers = { scout = 1.8, light = 1.4, medium = 1.0,
                              heavy = 0.7, support = 1.0, supply = 0.9 },
    UnknownClassSpeedMultiplier = 1.0,        // класс вне словаря идёт как medium
    AfterburnerSpeedMultiplier = 2.0,         // форсаж: x2 скорости…
    AfterburnerFuelPerSecond = 10,            // …и расход 10 ед топлива в секунду
    FuelCapacity = 100,                       // бак (спавн с полным)
    FuelRegenPerSecond = 2,                   // регенерация в обычном ходу, в форсаже — нет
}
```

Дефолт-трактовки движения (не подтверждены): топливо кончилось посреди участка — до его конца
скорость к базовой и форсаж там же не включается снова; регенерация идёт и когда корабль стоит
(«доехал до точки — стоит»); края карты не ограничивают движение (забота клиента);
поворот и коллизии НЕ делаются.

**Числа интеграции полного хода (`GameSessionTuning` в `GameSessionInterfaces.cs`)** — тоже
дефолты, не подтверждены: `WeaponRange = 300` ед — тик боя лэйна выполняется, когда живые
корабли его сторон сблизились ближе этого значения (базы сами не воюют); `SpawnOffsetPerPlayer = 30`
и `SpawnSpreadPerShip = 30` — дефолтная рассадка кораблей у домашней базы.

**Спец-роли классов (`ClassRolesConfig` в `ClassRolesInterfaces.cs`, кадр 4b).** Дефолты по
аналогии со стандартными RTS, НЕ подтверждены владельцем (правка = одна строка записи);
тесты задают свой конфиг:

```csharp
new ClassRolesConfig
{
    SupportRadius         = 300, // радиус аур (леченье/дозаправка), юнитов; дефолт, не подтверждено
    SupplyRadius          = 300, // тот же радиус по умолчанию; дефолт, не подтверждено
    SupportHealPerSecond  = 5,   // поддержка: +5 ед корпуса/сек живым союзникам (включая себя); дефолт
    SupplyFuelPerSecond   = 5,   // снабжение: +5 ед топлива/сек СВЕРХ регенерации; дефолт
    ScoutDamageMultiplier = 0.7, // scout ПОЛУЧАЕТ 70% урона (уклонение); дефолт, не подтверждено
    SupportClass = "support", SupplyClass = "supply", ScoutClass = "scout", // носители ролей
}
```

Ауры — такт спец-ролей в сессии СРАЗУ ПОСЛЕ движения: лечатся/дозаправляются только ЖИВЫЕ
союзники в радиусе, включая самого носителя. Scout-уклонение и спад урона от дистанции
работают через общий крючок `IShotDamageModifier` (множители перемножаются, дальше обычный
бой: щит → корпус).

**Спад урона от дистанции (`DamageFalloffConfig` в `DamageFalloffPolicy.cs`, P11).** Дефолты
НЕ подтверждены владельцем. Множитель выстрела «стрелок → цель» по дистанции d:
`d ≤ CloseRange` — урон полный (1.0); `CloseRange < d < WeaponRange` — линейный спад от 1.0
к полу; `d ≥ WeaponRange` — пол (там лейн боя и не тикает). Политика подключается
необязательным модификатором сессии; конфиг-заглушка `null` = прежнее поведение целиком.

```csharp
new DamageFalloffConfig
{
    CloseRange = 150, // до этой дистанции урон полный; дефолт, не подтверждено
    FarFloor   = 0.4, // пол спада на границе WeaponRange (300 из GameSessionTuning); дефолт
}
```

**Рейтинговая политика Эло (`EloConfig` в `RatingInterfaces.cs`, формула в `EloPolicy.cs`)** —
подключаемая схема счёта после исхода; схема — шахматного Эло FIDE, ступени K перезаписываются
под ICCup правкой конфига (одной записью). Политика выбирается при создании сессии (необязательный
параметр `ratingPolicy` конструктора/`StartFromRoom`); по умолчанию (и во всех существующих
тестах) работает прежняя плоская схема ±15/−10. Формула на игрока: `E_i = 1/(1+10^((R_oppTeamAvg_i
− R_i)/D))`, `R'_i = R_i + K_i×(S_i − E_i)`, где `R_oppTeamAvg` — средний рейтиг ВСЕХ противников
другой стороны (в 2v2 — двух), `S` = 1 / 0 / 0.5 (победа / поражение / ничья), K_i — по числу
rated-игр (Wins + Losses ДО исхода) и рейтингу. Сценарии-тесты — `tests/Rts.Domain.Tests/EloTests.cs`.

```csharp
new EloConfig
{
    StartRating = 0,              // старт новичка — фактически как у RatingRepository (Points = 0); дефолт
    D = 400,                      // разброс кривой ожиданий, классика FIDE; дефолт
    NoviceK = 40,                 // K, пока rated-игр меньше NoviceGamesThreshold; дефолт
    NormalK = 20,                 // K основного диапазона; дефолт
    MasterK = 10,                 // K с рейтинга MasterRatingThreshold и выше; дефолт
    NoviceGamesThreshold = 30,    // порог новичка по числу rated-игр; дефолт
    MasterRatingThreshold = 2400, // порог мастера по рейтингу; дефолт
    DrawScore = 0.5,              // очки S за ничью; дефолт
}
```

При плоской схеме ничья в сессии по-прежнему рейтингом не пишется (0/0, дефолт сохранён).
При подключённой Эло-политике сессия пишет ТАКЖЕ rated-ничью: `Apply(Draw)` — обе стороны
получают `S = EloConfig.DrawScore` (дефолт 0.5), счётчики Wins/Losses политика не растит.
Остальной ход ничьи в самой политике (`IRatingPolicy.Apply` — победа/поражение/ничья
считаются по составам сторон) — без изменений.

**Сознательные упрощения каркаса** (не баги, а осознанные границы MVP):
- Автоподбор лобби — «первая пара в очереди», а не подборе по рейтингу (P1 уточнится, когда появится рейтинг в лобби-сервисе).
- Попадание от дистанции есть: P11 внедрён политикой спада (`DamageFalloffPolicy`, дефолты `CloseRange = 150` / `FarFloor = 0.4`, см. §5); осознанно НЕ делались: метеориты, поворот корпусов и коллизии (в сессии бой лэйна стартует по триггеру дальности `WeaponRange` (дефолт 300), дальше «в первого живого»).
- Рейтинг — по умолчанию плоская схема ±15/−10 (одна пара победитель↔проигравший); при подключённой Эло-политике (`EloPolicy`, конфиг `EloConfig` — ступени K перезаписываются одной записью под ICCup) счёт ведёт политика по составам сторон, включая rated-ничью (S = DrawScore, дефолт 0.5); P15 «RatingService как внешний сервис» — после подтверждения схемы владельцем.
- Нет дуэлей-приглашений (P3) — короткая механика, добавим по надобности (Concede готов).
- Ничья в сессии: обе стороны уничтожены в один тик ИЛИ счёт лэйнов 1:1 («одинаковое уничтожение») → ничья; при плоской схеме рейтинг не пишется (0/0, дефолт), при Эло-политике — rated (обе стороны S = DrawScore).
- Вход напрямик (Confirm без запомненной почты) с профилем НЕ связывается — осознанно: для связки нужен почтовый адрес, а 2FA его не хранит; связка работает поверх обычного входа (`AccountLinkService`: запоминает почту этапа кодов, на Allowed ищет профиль по ней).
- 2v2-сессия: участники комнаты по порядку → 2A+2B, лобби-матчи крест-накрест (A0↔B0, A1↔B1); бои лэйнов независимы (пары дербятся каждая сама собой), общий исход — по всем кораблям стороны/лэйнам.

## 7. Что НЕ нужно переделывать при завтрашних правках

Завтра по плану: внос правки 2FA в доску + подтверждение хотспотов (метеорит, классы
кораблей, тик/DPS/HP, параметры щита, базы). Эти правки вписываются так:
- числа → **только** `BalanceConfig` (+1 строка на новое число, тесты задают свой конфиг);
- новая механика (метеорит, классы) → новый интерфейс/политика в `Interfaces.cs`,
  тесты (красные) → реализация; остальное не трогается;
- доска ES (`~/AI/es`, Vault .drawio) — источник контента: любое изменение правила
  сначала в модели, потом в каркасе — так доска и код не расходятся.

## 8. Словарик (для быстрого чтения кода)

- **Интерфейс** — контракт: имена методов, что должны означать, без реализации.
- **Реализация** — конкретный класс, работающий с обычной памятью (in-memory): дальше за
  этим же интерфейсом может встать БД/сеть, код выше не узнает.
- **Политика** — «правило, которое решает»: при каком событии что запускать
  (пример: TwoFactorAuthenticator, правило таймаута лобби, правило гашения щита).
- **Конфиг баланса** — все изменяемые числа игры в одном record.
- **TDD-цикл** — тесты первыми (красные) → реализация до зелёного прогона.
